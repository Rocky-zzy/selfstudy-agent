## 一、用户原话（逐字）

**Q1 交付物形态**
> 「能跑的 agent，最终一定要投入使用，**以项目为第一目的而研究是次要目的**。」

**Q2 时间**
> 「由浅入深的慢慢做，没有必须的时间要求，大概是 **3 个月**的时间，非常充裕。」

**Q3 数据 / 被试**
> 「这个项目过程中**只有我一个人可以当被试**，在明年春天投入使用后才会有大量的数据。」

**Q4 项目设想（最长、最关键的一段）**
> 「既然是以项目落地为主而不是研究发论文，不用那么在意贡献点，我的思路就是做出来一个首先传入课件（如 math for ai 或者什么离散数学或者其他的），然后**冷启动的知识点讲解或者例题的讲解**，通过我们对 **agent 的讲解方式的优化、知识图谱的搭建**，能使得这个过程达到**大部分人百分之 70 的满意度**（**超过相同 LLM 冷启动**的情况），然后**在用户两到三轮的交互**（如他注入他的偏好，他的反馈之后），通过**条件-策略的方式**使得自学体验更加贴合这个用户个人，提升满意度。**长期交互中构建学生画像**，来进一步提升自学的满意度。这就是我的设想。」

**Q5 课程范围**
> 「目前暂时用这个，最终这个项目落地的时候是**用于离散数学的自学**，那个资料后面可能会有。**不用搭建完整的知识图谱，挑选几章强相关的来搭建就行**，教材只是相当于一个接口而已，我们要把程序做好。（但是目前**先不追求通用**不然又乱了）。」

**Q6 用户规模**
> 「**两百名学生**。但是正如我说的我们要先搭建好这个能跑的 agent，再明年春季学期投入使用后才能收数据。」

## 二、由定调推导出的三阶段规格

| | **阶段一 冷启动** | **阶段二 短期适配** | **阶段三 长期** |
|---|---|---|---|
| 输入 | 课件 | 课件 + 用户偏好/反馈 | 课件 + 长期交互历史 |
| 干什么 | 知识点讲解 / 例题讲解 | 用**条件-策略**适配 | 构建**学生画像** |
| 两个杠杆 | **① 讲解方式优化<br>② 知识图谱搭建** | 条件-策略 | 画像 |
| 指标 | 大部分人 **≈70% 满意度**，且**优于同款 LLM 冷启动** | 满意度提升 | 满意度进一步提升 |
| 交互轮次 | 0 | 2–3 轮 | 长期 |

**主指标是满意度**，且**有一个明确的对照组**："相同 LLM 冷启动"。这一点很重要——**没有基线，70% 这个数字没有意义**。

## 三、架构含义：分层视图

把定调与已有的 ITS 架构分解（经典三模型：**student model / pedagogical model / content model**）合并，得到下面的分层。**每一层都是一个可能的贡献点，也都是一种可能的"卡死"来源。**

```
┌──────────────────────────────────────────────────────────────┐
│  L4  交互与反馈层                                              │
│      对话管理、何时追问、何时给检验任务、如何收尾               │
├──────────────────────────────────────────────────────────────┤
│  L3  讲解实现层  ——「讲得好」（阶段一杠杆①）                    │
│      给定范围与深度，把内容说到学生能往下走一步                  │
├──────────────────────────────────────────────────────────────┤
│  L2  教学决策层  ——「讲得全不全」+ 条件-策略（阶段一/二）        │
│      决定：讲什么、讲到多全、聚焦哪个重难点／易错点              │
│      输入：L1 学生状态 + L0 知识结构 + 本次请求/偏好/反馈        │
├──────────────────────────────────────────────────────────────┤
│  L1  学生状态层（学生模型）—— 阶段二/三                         │
│      他掌握了什么、薄弱在哪、易错点在哪                          │
├──────────────────────────────────────────────────────────────┤
│  L0  内容与结构层                                              │
│      知识库（已建成）+ 知识结构（知识点 / 前置关系 / 易错点）     │
│      ← 阶段一杠杆②「知识图谱搭建」落在这里                      │
├──────────────────────────────────────────────────────────────┤
│  L5  评估层（横跨）                                            │
│      满意度（主）／内容准确／对照组比较                          │
└──────────────────────────────────────────────────────────────┘
```

### 我们目前的资产在这张图上的分布

| 层 | 资产 | 状态 |
|---|---|---|
| L0 内容 | `knowledge_base/` 128 chunks | ✅ 有料 |
| **L0 结构** | —— | ❌ **空白** |
| **L1 学生状态** | —— | ❌ **空白** |
| L2 决策 | `docs/02` 策略×条件（未验证） | ⚠️ 框架有 |
| **L3 实现** | 此前绝大部分精力都投在这里 | ⚠️ **过度投入** |
| **L4 交互** | —— | ❌ **空白** |
| L5 评估 | 满意度：尚未定义 | ❌ 空白 |

**这张表解释了此前"越做越接不上"的原因**：L3 的上游（L0 结构、L1）与下游（L4）都没定，L3 就没有验收标准。

## 四、关键澄清：之前的三个纠结，在定调之后自动消解

| 之前的纠结 | 定调之后 |
|---|---|
| "讲得好"还是"讲得全"？ | **不是二选一**：全不全是**决策层**，好不好是**实现层** |
| 用户本人的判断能不能当标准？ | **满意度是产品指标，按定义主观，不需要研究级效度**。（但它不能用来声称"讲解质量更高"） |
| 评估要做到什么程度？ | **以满意度 + 与基线对比为主**，不做学习增益实验（需要真人被试且我们只有一个） |

## 五、明确的项目约束（写死，防止范围蔓延）

1. **教材是接口，程序是本体**——不要把精力花在课程内容本身上。
2. **不追求通用**——先把一门课（离散数学）做好。
3. **知识图谱只搭"几章强相关的"**，不搭整门课。
4. **先有能跑的系统，再谈优化**——不要在系统存在之前先造评估工具（已有一次代价高昂的教训，见 `docs/04`）。
5. **开发期只有用户一个被试**——所有"满意度"结论都是 n=1 的，只能作为方向性判断。

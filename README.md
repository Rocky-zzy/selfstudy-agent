## 一、项目定调（用户 2026-09-17 确定）

**一句话**：给一门课的自学学生一个能讲解知识点 / 例题的 Agent；先做到**冷启动讲解让大多数人满意**，再通过**短期交互适配**与**长期画像**逐步贴合个体。

| 项 | 内容 |
|---|---|
| **目标形态** | **能跑的 agent，最终必须投入使用**。以**项目落地为第一目的**，研究发论文为次 |
| **时间** | 约 **3 个月**，无硬截止，由浅入深慢慢做 |
| **最终场景** | **离散数学**的自学（课件后续提供）。当前暂用 **AIAA 2711** 课件作试验场 |
| **关键约束** | **教材只是一个接口**——重点是**程序做好**；**暂不追求通用**（追求通用会乱） |
| **被试** | 开发期**只有用户本人**；**约 200 名学生**要等明年春季投入使用后才有数据 |

### 三阶段路线（用户设想）

| 阶段 | 做什么 | 目标指标 |
|---|---|---|
| **阶段一：冷启动** | 传入课件 → **知识点讲解 / 例题讲解**。靠两个杠杆：**① 讲解方式优化 ② 知识图谱搭建** | 让**大部分人达到约 70% 满意度**，且**优于"同款 LLM 冷启动"** |
| **阶段二：短期适配** | 用户注入偏好、给出反馈（**2–3 轮交互**）→ 用**条件-策略**方式适配 | 自学体验更贴合该用户，**满意度提升** |
| **阶段三：长期** | 长期交互中构建**学生画像** | 进一步提升满意度 |

**主指标 = 满意度**（**不是**学习增益）。

### 范围限制（写死，防止跑偏）

- **不搭建完整知识图谱**，只**挑选几章强相关的**来搭
- **不追求通用**，先把这一门课的 agent 做好
- 教材/课件是可替换的接口，不是研究对象

## 二、两个关键判断（由用户提出，已并入架构）

### 1. 「讲得好」与「讲得全不全」不在同一层级

- **讲得全不全 = 决策层**：给谁、讲到什么范围、聚焦哪个重难点／易错点 → **依赖知识图谱 + 对学生个人的判断**
- **讲得好不好 = 实现层**：决策定了之后，这段内容**怎么被说出来**

两者**不冲突、不需要二选一**。同一个知识点，"讲全"和"只突破难点"是两种不同的"好"——**所以"讲得好"离开决策就没有验收标准。**

### 2. 满意度作为产品指标，与作为研究构念，标准不同

此前我们纠结过"用户本人的判断不是权威标准"。**在这个项目里这个纠结不成立**：

- 满意度**按定义就是主观的**，它就是产品指标，**不需要**达到研究量表那种构念效度；
- 研究意义上的"讲得好"（与学习增益挂钩）是**另一件事**，本项目**不作为主指标**。

→ **结论：开发期用用户本人的满意度评分是完全正当的**，不必为它找文献背书。但要清楚它**不能**用来声称"讲解质量更高"。

## 四、第一阶段该做什么（建议的第一步）

阶段一的两个杠杆是**讲解方式优化**与**知识图谱搭建**。按总原则（先证必要性），建议顺序：

1. **先搭一个能跑的最小闭环**：课件 → 检索相关 chunk → LLM 生成讲解 → 用户读 → **打满意度分**。
   - 产物是**基线**（"同款 LLM 冷启动"）。没有基线，后面所有比较都无从谈起。
   - ✅ **已完成**（2026-09-17）：见 `app/`，操作见 `docs/06_怎么跑起来.md`，设计与实测记录见 `docs/05_最小闭环与基线.md`。
   - ⏳ **卡在这里**：**等用户本人实测打分**。系统能跑不等于有基线——基线是"分数"，不是"代码"。
2. **再搭"最小知识结构"**：从 `knowledge_base` 里选**一章**，抽出知识点 + 前置关系 + 易错点。
   - 不要一上来建整门课的图谱（用户已明确范围限制）。
   - ⚠️ 动工前先过 `docs/00` §三：**「教学卡」目前状态仍是待证明**。
3. **然后才谈"讲解方式优化"**：有了基线，才知道要改什么、改了多少。
   - 目前 `optimized` 条件已按 `docs/03` §六 落地 4 条有出处的约束；**它是否有效，要等实测裁决**。

> ⚠️ **不要先从"评估量表"入手。** 我们已经在这上面栽过一次（见 `docs/04`）：在没有可运行系统之前先造评估工具，结果整轮实验作废。**先有系统，再有度量。**
